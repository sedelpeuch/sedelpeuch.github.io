Les [traces](./2026-11-08-opentelemetry-traces.md) produites par une application instrumentée doivent être stockées quelque part, puis retrouvées : par leur identifiant quand un log ou une métrique y renvoie, par leurs caractéristiques quand la question est "quelles requêtes ont échoué dans la dernière heure". Une trace pèse vite plusieurs kilo-octets et un service actif en produit des milliers par minute, ce qui rend coûteuse toute indexation fine. Grafana Tempo est un backend de traces conçu pour ce volume : il stocke les traces en blocs dans un stockage objet, sans index par attribut, et compense par un langage de requête et par des métriques calculées à partir des spans. Cet article décrit son fonctionnement, la recherche avec TraceQL et le *metrics-generator*.

<!--truncate-->

## Stocker sans indexer

Tempo reçoit les spans en OTLP (ainsi qu'aux formats Jaeger et Zipkin), les regroupe par trace en mémoire, puis écrit des blocs au format Parquet dans un stockage objet : S3 ou un service compatible, GCS, Azure, ou un simple répertoire local pour un usage restreint. Il n'entretient aucun index par attribut, ce qui rend l'écriture et le stockage peu coûteux.

Retrouver une trace par son identifiant reste rapide, chaque bloc indiquant les identifiants qu'il contient. C'est le cas d'usage principal : un log, un exemplar ou un lien depuis une autre trace fournit le `trace_id`. La recherche par attributs, elle, lit les colonnes Parquet des blocs de la période demandée, ce qui la rend plus lente à mesure que la période s'allonge.

Tempo se déploie en **mode monolithique**, un seul binaire qui joue tous les rôles, ou en **microservices** (distributeur, ingesteur, querier, compacteur…) mis à l'échelle séparément. Pour quelques services et quelques requêtes par seconde, le mode monolithique avec un stockage local suffit ; le stockage objet devient nécessaire dès qu'il faut répliquer ou conserver longtemps.

## TraceQL

**TraceQL** sélectionne des spans par leurs attributs et renvoie les traces qui les contiennent. Une requête s'écrit entre accolades :

```text
{ resource.service.name = "colis" && span.http.response.status_code >= 500 }
```

Le préfixe désigne la portée de l'attribut : `resource.` pour la ressource du service, `span.` pour les attributs du span. Des champs intrinsèques s'utilisent sans préfixe : `name`, `kind`, `status`, `duration`. Quelques requêtes types :

- `{ status = error }` : les traces qui contiennent au moins un span en erreur ;
- `{ resource.service.name = "suivi" && duration > 500ms }` : les spans lents d'un service ;
- `{ span.suivi.colis.id = 42 }` : les traces d'un objet métier, grâce à un attribut posé à la main.

Le langage exprime aussi des relations entre spans : `{ resource.service.name = "colis" } >> { status = error }` cherche les traces où un span de `colis` a un descendant en erreur, autrement dit une panne située en aval de ce service.

## Le metrics-generator

Les traces répondent à des questions sur une requête ; les questions sur un ensemble de requêtes ("quel est le débit de cette opération ?") demandent des métriques. Le **metrics-generator** de Tempo calcule ces métriques à partir des spans reçus et les écrit dans Prometheus par *remote write*. Il comprend deux processeurs principaux.

### Span metrics

Le processeur `span-metrics` compte les spans et mesure leur durée, regroupés par service, nom de span, type et statut. Il produit `traces_spanmetrics_calls_total` et l'histogramme `traces_spanmetrics_latency`. Ces métriques couvrent des cas que les métriques du SDK ne couvrent pas :

- les **spans manuels** : une étape métier découpée à la main obtient son débit, son taux d'erreur et ses percentiles sans qu'aucune métrique ait été écrite dans le code ;
- les **composants qui produisent des traces sans métriques** par application, comme un reverse proxy dont chaque route devient mesurable.

Chaque combinaison de dimensions crée une série. Des noms de spans non génériques (un identifiant dans le nom) ou des spans techniques nombreux font exploser leur nombre ; un filtre sur les noms ou les types de spans le maîtrise.

### Carte des services

Le processeur `service-graphs` repère les paires de spans `CLIENT` et `SERVER` liées par une relation parent-enfant, et en déduit les appels d'un service à un autre, avec leur débit, leurs erreurs et leur durée (`traces_service_graph_request_total` et ses variantes). Un appelant non instrumenté, un navigateur ou un outil en ligne de commande, apparaît comme un nœud `user`. Un appelé non instrumenté, une base de données ou une API externe, apparaît sous le nom tiré des attributs du span `CLIENT` (`db.system.name`, `server.address`), comme nœud virtuel. Grafana dessine cette carte dans la vue *Service Graph* de la datasource Tempo.

### Exemplars

Avec `send_exemplars: true`, le metrics-generator joint aux histogrammes qu'il écrit des exemplars pointant vers les traces d'origine. Ils portent l'identifiant dans un label `traceID`, alors que les exemplars produits par les SDK OpenTelemetry utilisent `trace_id`. La datasource Prometheus de Grafana doit déclarer les deux noms dans `exemplarTraceIdDestinations` ; avec un seul, une partie des exemplars s'affiche sans lien vers la trace.

## Consultation dans Grafana

La datasource Tempo de Grafana propose trois entrées :

- **Explore** avec TraceQL ou un constructeur de requêtes, pour une question précise ;
- **Traces Drilldown**, une application de navigation à la souris, sans requête : débit, erreurs et répartition des durées, découpage par attribut, comparaison entre une sélection et le reste ;
- la vue **Service Graph**, alimentée par les métriques du metrics-generator.

Dans une trace ouverte, la cascade se filtre par attribut, et les vues *Critical path* et *High latency* mettent en évidence les spans qui portent la durée de la requête.

## Limites

- **Recherche par attributs coûteuse** : sans index, une recherche sur une longue période lit beaucoup de blocs. La rétention et la largeur des périodes interrogées sont à dimensionner ensemble.
- **Métriques dérivées et échantillonnage** : le metrics-generator ne voit que les traces conservées. À 10 % d'échantillonnage, ses compteurs doivent être multipliés par dix, et les métriques du SDK restent la référence pour les alertes.
- **Cardinalité** : les dimensions des span metrics s'ajoutent les unes aux autres ; chaque attribut ajouté multiplie le nombre de séries dans Prometheus.
- **Stockage objet** : au-delà du mode monolithique local, Tempo dépend d'un stockage S3 ou équivalent à opérer à côté.

## Conclusion

Tempo stocke les traces en blocs Parquet dans un stockage objet, sans index par attribut : la recherche par identifiant est immédiate, la recherche par attributs passe par TraceQL et lit les blocs de la période. Le metrics-generator transforme le flux de spans en métriques Prometheus, ce qui donne un débit, un taux d'erreur et une latence à chaque opération tracée, spans manuels compris, ainsi qu'une carte des appels entre services. Les exemplars qu'il produit relient ces métriques aux traces, à condition que Grafana connaisse le nom du label qui porte l'identifiant.
